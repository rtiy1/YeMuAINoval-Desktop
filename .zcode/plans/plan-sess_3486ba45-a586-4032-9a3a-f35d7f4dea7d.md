## 第 2 块:会话历史持久化

### 设计

新增 `agent_messages` 表,存储每个会话的消息(用户 + 助手)。WS send handler 写用户消息,result 事件写助手消息。前端加载时从 REST 恢复。

### 2.1 数据库 schema

**修改 `apps/backend/src/db/schema.ts`** — 新增 `agentMessages` 表:

```ts
export const agentMessages = sqliteTable('agent_messages', {
  id: text('id').primaryKey().$defaultFn(() => nanoid()),
  agentSessionId: text('agent_session_id').notNull()
    .references(() => agentSessions.id, { onDelete: 'cascade' }),
  role: text('role').notNull(), // 'user' | 'assistant'
  content: text('content').notNull(),
  toolCalls: text('tool_calls'), // JSON 序列化的 ToolCallGroup[]
  durationMs: integer('duration_ms'), // 仅 assistant
  costUsd: real('cost_usd'), // 仅 assistant
  numTurns: integer('num_turns'), // 仅 assistant
  isError: integer('is_error', { mode: 'boolean' }).default(false),
  sortOrder: integer('sort_order').notNull().default(0),
  createdAt: text('created_at').notNull().$defaultFn(now),
});
```

**修改 `apps/backend/src/db/index.ts`** — initDb 加 `CREATE TABLE IF NOT EXISTS agent_messages`。

### 2.2 后端路由

**新建 `apps/backend/src/routes/messages.ts`**:

```
GET  /api/sessions/:id/messages → 按 sortOrder 排序返回所有消息
```

返回结构对齐前端 ChatMessage 类型: `{id, agentSessionId, role, content, toolCallGroups?, durationMs?, costUsd?, numTurns?, isError?, createdAt, sortOrder}`。

### 2.3 后端:WS send handler 写用户消息

**修改 `apps/backend/src/ws/agent-events.ts`** — `send` handler 在调用 buildAgentMessage 之前,把用户消息写入 agent_messages 表:

```ts
case 'send': {
  // ...现有校验
  // 持久化用户消息
  const db = getDb();
  const [lastMsg] = await db.select().from(schema.agentMessages)
    .where(eq(schema.agentMessages.agentSessionId, msg.agentSessionId))
    .orderBy(desc(schema.agentMessages.sortOrder)).limit(1);
  const nextSort = (lastMsg?.sortOrder ?? 0) + 1;
  await db.insert(schema.agentMessages).values({
    agentSessionId: msg.agentSessionId,
    role: 'user',
    content: msg.content,
    sortOrder: nextSort,
  });
  // ...现有 buildAgentMessage + bridge.sendMessage
}
```

### 2.4 后端:bridge result 事件写助手消息

**修改 `apps/backend/src/mcode/bridge.ts`** — `handleOutput` 的 `result` 分支:在 emit 之前,需要把当前 assistant 消息(流式累积的内容 + toolCallGroups)持久化。

但 bridge 不知道 agentSessionId 与消息内容的对应关系(它只 emit 事件)。更好的方案:**在 WS 层持久化**,因为 WS 层知道 agentSessionId。

**方案:在 agent-events.ts 的事件广播处理器中拦截 result 事件**,但这样需要累积 assistant 内容。

**最终方案:用一个新的 WS 消息类型 `persist_assistant`**,由前端在 `assistant_done` 时发送。但这改变了数据流方向。

**更简洁的方案:在后端 bridge 里维护一个 per-session 的 assistant 内容缓冲**:
- `text_delta` → 追加到缓冲
- `tool_use` → 追加到 toolCalls
- `result` → 把缓冲内容写入 agent_messages 表,清空缓冲

**修改 `apps/backend/src/mcode/bridge.ts`**:
- MCodeSession 结构新增 `contentBuffer: string`、`toolCallBuffer: ToolCall[]`
- handleOutput 的 assistant/text_delta/stream_event 分支:追加到 session.contentBuffer / session.toolCallBuffer
- handleOutput 的 result 分支:emit 事件后,异步写 DB

但这引入了 bridge 对 DB 的依赖。bridge 已经在 loadModelEnv 里动态 import db,所以这可行。

**实际实现**:在 bridge.ts 的 `emit` 方法里,如果是 result 事件,同时写 DB:

```ts
private async emit(agentSessionId: string, kind: string, payload: unknown) {
  // 现有:广播给 WS 订阅者
  this.handler?.({ kind, sessionId: '', agentSessionId, payload });

  // 新增:result 事件时持久化 assistant 消息
  if (kind === 'result' && agentSessionId) {
    const session = this.sessions.get(agentSessionId);
    if (session && session.contentBuffer) {
      // 异步写入,不阻塞事件流
      this.persistAssistantMessage(agentSessionId, session, payload as MCodeResult);
    }
  }
}
```

## 风险与取舍

1. **appendSystemPrompt 仅首次创建会话生效**:ensureSession 首次创建后早返回,config 变更不重新 spawn。写作风格在会话创建时固定,已有会话改了 writing_style 需新建会话才生效。前端编辑器旁会注明此限制。
2. **assistant 消息持久化在 bridge 层**:bridge.ts 将新增对 DB 的写入依赖(动态 import,与 loadModelEnv 一致)。contentBuffer 在内存累积,result 时一次性写入。如果 MCode 进程崩溃(result 事件未发出),缓冲内容会丢失——这是可接受的(崩溃的会话本就不完整)。
3. **token 统计是估算**:contextUsed 仍用 numTurns * 3000 估算(MCode result 事件不带真实 token counts)。costUsd 是真实值。
4. **历史消息加载时机**:仅当 session 首次加载时从 REST 拉取,后续流式消息正常追加,不重复加载。
